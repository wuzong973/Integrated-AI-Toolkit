## 二、逐项目详细分析

### A1. presenton — AI PPT 生成（Apache-2.0）

- **核心功能**：提示词/上传文档 → 生成可编辑 PPTX/PDF；拖拽编辑器；HTML+Tailwind 声明式模板体系；BYOK 多 LLM/图像 Provider；MCP Server；多用户工作区。
- **技术栈**：Next.js + FastAPI(Python)，Docker 一键部署 / Electron。
- **活跃度**：v0.9.11-beta（2026-09-21），迭代快但仍在 0.x beta，breaking change 频繁。
- **适配**：对应 `generate_ppt`。不建议整体引入（自成一体产品），借鉴其「模板 → slide 结构 → python-pptx 导出」管线与 API 设计在 `services/ai` 自建。难度：中。
- **借鉴**：声明式模板体系；AI Provider 可插拔层；standard/smart 双生成模式配置化。

### A2. docling — 万能文档解析（MIT）⭐

- **核心功能**：PDF/DOCX/PPTX/XLSX/HTML/图片/音频等 20+ 格式解析；版面、阅读顺序、表格、公式理解；统一 DoclingDocument 中间模型；导出 Markdown/HTML/JSON；内置 OCR 与 VLM 管线；docling-serve 提供 REST API。
- **技术栈**：Python 库（pip），Pydantic v2，可容器化独立服务。
- **活跃度**：v2.135.0（2026-10-07），几乎周更；IBM 发起、LF AI & Data 托管，社区大。
- **适配**：直接升级 `parse_document` / `convert_pdf`：pip 进 `services/ai`，封装 DocumentParser Provider；重负载场景改用 docling-serve 独立容器。难度：低-中。风险：模型依赖重（镜像体积/CPU 耗时），需对齐 `check:timeout-budget`。
- **借鉴**：统一中间文档模型 + 多格式导出；标准/VLM 双管线可切换的 pipeline 抽象。

### A3. PaddleOCR — 中文 OCR（Apache-2.0）

- **核心功能**：PP-OCRv4/v5 多语言 OCR（中文最强）；版面分析、表格识别、关键信息抽取（PP-Structure）；训练-压缩-部署全链路。
- **技术栈**：Python（Paddle 框架），产线化 API，Serving/Mobile/Docker 多端部署。
- **活跃度**：v3.7.0（2026-06-11），百度背书，中文 OCR 事实标准。
- **适配**：增强 `ocr_image`（票据/试卷/手写场景）。Python 库进 `services/media`，封 OCR Provider。难度：中。风险：Paddle 生态依赖大（GB 级镜像），建议裁剪 mobile 轻量模型。
- **借鉴**：「产线」封装——一条 API 内聚检测+方向分类+识别+版面的模型编排。

### A4. faster-whisper — 自托管 ASR（MIT）⭐

- **核心功能**：Whisper 的 CTranslate2 重实现，速度至 4×、显存减半；词级时间戳；Silero VAD；批量推理；int8 量化。
- **技术栈**：Python 库（pip），依赖 CTranslate2/PyAV（免装 FFmpeg），CPU/GPU 通用。
- **活跃度**：v1.2.1（2025-10-31），迭代放缓但已成熟稳定，生态庞大（WhisperX 等基于它）。
- **适配**：自托管 `speech_to_text` 降本。pip 进 services，封 ASR Provider；CPU 跑 int8+small/distil 控制成本。难度：低。风险：中文标点需后处理；长音频分片后必须与 `ASR_TOTAL_BUDGET_MS` 客户端超时对账（否则复现「两端判定相反」的老问题）。
- **借鉴**：segments 生成器惰性输出适合流式；BatchedInferencePipeline 吞吐优化思路。

### A5. markmap — Markdown→思维导图（MIT）

- **核心功能**：markmap-lib 解析、markmap-view 渲染（d3）、toolbar/autoloader，VSCode/MCP 插件生态。
- **技术栈**：TS 单仓多包 npm 库，纯前端渲染，无服务端。
- **活跃度**：GitHub release 停在 v0.18.0（2024-12），单人维护、迭代放缓；npm 子包偶有更新。**须锁版本**。
- **适配**：`generate_mindmap` 只读展示路径：LLM 产 Markdown → H5/web-view 渲染导图或服务端渲染出分享图。难度：低。风险：原生小程序不能直接跑 DOM 库。
- **借鉴**：Markdown 即数据源，生成与渲染解耦；common/lib/view 分层。

### A6. mind-elixir-core — 可交互思维导图编辑器（MIT）

- **核心功能**：拖拽/多选/撤销重做、节点连线与概要、SVG/PNG 导出、主题+CSS 变量、触屏支持。
- **技术栈**：TS npm 库（mind-elixir），vanilla JS 零重依赖。
- **活跃度**：v5.15.1（2026-08-05），单人高频迭代，changelog 详尽。
- **适配**：`generate_mindmap` 的「可编辑」二期升级：AI 生成数据导入 → H5 页编辑 → 回存。难度：中（web-view 承载 + 双向通信 + 域名鉴权）。风险：v5 仍有 breaking change。
- **借鉴**：operation 事件总线 + before 操作守卫（天然适配审计/协同）；节点数据自带 id/样式利于持久化。

### A7. mermaid — 文本即图表（MIT）

- **核心功能**：文本 DSL → 20+ 图型（流程/时序/甘特/ER/状态/思维导图）；主题定制；sanitize+沙箱安全渲染。
- **技术栈**：TS npm 库，浏览器 SVG 渲染；服务端出图走 mermaid-cli（puppeteer）。
- **活跃度**：mermaid@12.1.0（2026-10-02），数千贡献者，顶级社区。
- **适配**：a) 分享页/H5 内嵌渲染 UGC 图表；b) `generate_document`/PPT 配图：LLM 产 mermaid DSL → 服务端渲染 PNG。难度：低-中。风险：LLM 产 DSL 有语法错率，需校验+重试；puppeteer 较重。
- **借鉴**：文本即图表、可版本化；UGC 必须走其 sanitize/沙箱方案。

### A8. ComfyUI — 节点式图像生成（GPL-3.0 ❌）

- **核心功能**：节点/流程图编排扩散模型（SD/Flux 图像、视频、音频）；异步队列；增量执行；工作流 JSON/PNG 内嵌。
- **技术栈**：Python+PyTorch，桌面版 + API 后端。主仓库已迁至 Comfy-Org/ComfyUI。
- **活跃度**：v0.39.0（2026-10-05），月均数版，75k+ stars，公司化运营。
- **适配**：GPL 禁止进 apps/services。仅两条路：独立部署实例经 **API 调用**（网络输出不传染）作图片生成 Provider；或优先云端文生图 API。难度：高（GPU 运维+合规）。
- **借鉴**：增量执行与队列调度可供 `services/media` 借鉴；「工作流 = 可版本化 JSON」编排结构。

### A9. deepwiki-open — 仓库→Wiki 文档生成（MIT）

- **核心功能**：输入仓库 URL → 代码结构分析 → 生成多页 Wiki（文档 + Mermaid 图 + codemap + RAG 追问）。
- **技术栈**：FastAPI + Next.js，多模型（OpenAI/Gemini/Ollama），Docker。
- **活跃度**：18.1k stars；无 release tag 直接 main 迭代（2026-09 仍在推送），中速活跃。
- **适配**：AI 学习分类新能力「仓库解读」：自托管后经 Provider 接入，AI 助手出 Wiki 结果卡。难度：中。风险：LLM token 成本与内容合规。
- **借鉴**：「文档+图+可追问」三位一体结果卡结构；per-repo 持久化与增量刷新。

## 四、技术可行性分析

1. **最稳路线 = Python 库 + Provider 封装**：docling、faster-whisper、PaddleOCR 均为 pip 可装、MIT/Apache 许可，与 `services/ai`、`services/media` 现有形态完全一致；统一在 `packages/core/src/providers` 增加/扩展接口即可，不破坏「外部依赖只走 Provider」红线。
2. **小程序侧限制是最大约束**：markmap/mind-elixir/mermaid 都是 DOM 库，原生小程序不能直接跑。可行路径只有三条：H5 分享页（web-view）、服务端渲染出图（mermaid-cli/markmap-cli）、或导出静态图。前两者成本低，web-view 需要域名备案+鉴权，是二期成本。
3. **资源与超时风险**：docling/PaddleOCR 模型镜像重（GB 级）、CPU 推理慢；自托管 ASR/PDF 服务都要过 `check:timeout-budget` 三处对账（源码默认值 + `.env.example` + `.env`），否则复现「用户看到超时、服务端仍在跑」的判定相反问题。
4. **许可证风险已全部实证**：GPL/AGPL/品牌条款项目（it-tools、prompt-optimizer、open-webui、ComfyUI）一律不集成；Stirling-PDF 只用社区目录；任何引入先登记 `docs/compliance/OPEN_SOURCE_LICENSES.md`。
5. **维护性风险**：markmap（单人、release 停更）与 mind-elixir（单人、v5 breaking）都需锁死版本；docling/presenton 迭代极快，建议用锁定的次版本号 + 定期升级窗口。

## 五、设计借鉴建议（跨项目共性）

1. **「工具即目录」规范**（omni-tools/it-tools）：一个目录 = 元数据 + 纯函数 + UI + i18n + 测试，脚本生成脚手架——与现有工具箱扩展模式同构，值得在 `check:tools` 之外再固化一层目录约定。
2. **统一中间模型**（docling 的 DoclingDocument、markmap 的 Markdown 源、mermaid 的 DSL）：生成与渲染解耦，LLM 只产中间格式，渲染层可换——适配 AI-OUTPUT-QUALITY-STANDARD 的「图表多样性」要求。
3. **声明式能力注册**（open-webui 的 Pipe/Tool、LibreChat 的 SKILL.md）：一个函数/一个文件即一个能力，天然可静态校验——与 `check:ai-capabilities` 的「能力目录 ⊆ seed ∩ 执行器」断言互为印证，可简化五步接入清单。
4. **评估驱动的质量闭环**（prompt-optimizer）：生成 → 评分 → 对比 → 迭代，直接映射到现有质检环节。
5. **目录级许可证隔离**（Stirling-PDF）：若未来自有仓库引入 open-core，这是可抄的写法。

## 七、执行注意事项

- 每引入一个依赖，先登记 `docs/compliance/OPEN_SOURCE_LICENSES.md`，再走五步接入清单（`docs/dev/AI-CAPABILITY-DISPATCH.md`）；
- 新增能力必须同步 seed 与执行器，交付前跑 `npm run check:ai-capabilities`（能跑却没进目录也会报）与 `check:tools`；
- 涉及长任务（OCR/文档解析/ASR）的服务端预算与客户端超时，交付前必须过 `check:timeout-budget` 三处对账；
- AI 产出类新能力（mermaid DSL、mindmap、Wiki）在提示词中注入 `AI-OUTPUT-QUALITY-STANDARD` 的字数/多样性要求，交付前过 `check:ai-output-quality`。
