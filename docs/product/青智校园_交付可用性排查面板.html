P0阻断交付的问题

P0-1编排看板用硬编码假数据冒充真实编排结果（违反项目红线）
现象进入「编排看板」看到目标「举办 200 人创新创业活动，预算 3000 元」与 8 个节点（含「已发布 · 3人报名」），界面上没有任何演示标记，与真实结果无法区分。
证据pkg-os/plan/index.ts:168-177 的 catch 分支直接 applyRun(buildDemoRun())，只设 loading:false，未设任何 demo 标记；index.wxml 中 grep 演示|demo = 0 命中。
必然触发GET /os/runs/:id 实测 404 → 只要点进这个页面，看到的一定是假数据。
反差项目已建好 demoMode 机制（utils/request.ts:53），首页与 AI 页都正确挂了「演示模式」角标，唯独这一页没用。
修复方案
  • 最小改动：catch 里 setData({demo:true})，WXML 顶部挂「演示模式」角标（复用 pages/home/index.wxml:69 的 .status-badge）
  • 更彻底：与 order-list 对齐 —— 改为不发请求 + showNotReady，彻底不展示假数据
  • 加守卫：含 DEMO_* 常量的页面必须引用 demoMode
P0-2Redis 未运行，作业队列已降级为进程内执行
证据启动日志 WARN Redis 不可用，降级运行；/health 返回 redis:"down"、queue.degraded:true；端口 6379 无监听；Redis 仅由 compose 提供，而本机 docker: command not found。
真实代价降级路径能跑通（作业 6 秒成功），但：无跨进程并发控制、作业状态不持久（进程重启即丢）、无死信统计（返回 -1 不可知）、无 PEL 无法重投。
做得对的降级不静默：打 warn + /health 暴露 degraded:true，符合 M0-11 判据。这一条不需要返工。
修复方案
  • 装 Docker Desktop 或本机 Redis 7，使 docker compose up -d redis 可用
  • docs/dev/ENV.md 增加「Redis 为生产必需组件，缺失禁止上线」
  • /health 的 status 在 degraded=true 时从 ok 降为 degraded —— 现在仍是 ok，监控会漏报
P0-3小程序端后端地址不可用于真机与线上
证据utils/env.ts：develop: 'http://127.0.0.1:3000'（真机上指向手机自己）；trial/release 指向 api-staging.qingzhi.example.com / api.qingzhi.example.com —— example.com 是 RFC 2606 保留占位域名，永远解析不到；且 const ENV='develop' 是编译期硬编码，无构建期切换。
连带STORAGE_PUBLIC_BASE_URL 为空 → 回落 localhost → 真机上文件下载地址指向手机自己。
影响M0-16「真机登录成功」这条验收线物理上不可能通过。
修复方案
  • ENV 改为由 wx.getAccountInfoSync().miniProgram.envVersion 自动推导，避免手工改常量
  • 真机调试：基址改为局域网 IP 或内网穿透，并抽成构建注入，不写死在源码
  • trial/release 填真实域名（须已备案 + HTTPS + 加入小程序 request 合法域名）
  • 同步设置 STORAGE_PUBLIC_BASE_URL；补《真机联调前置清单》

P1影响可用性的问题

P1-14 个页面已注册路由，但界面里没有任何入口
证据全仓库 grep（排除自身目录与 app.json），入站引用均为 0 处：pkg-station/service、pkg-station/provider、pkg-station/apply、pkg-station/order-detail。且 order-list 中没有任何 navigateTo。
反差order-detail 是已写好真实交互的页面（支付/验收/退款均 await 真实接口 + showNotReady 兜底），却因无入口而白写。
修复方案
  • order-list 列表项补 bindtap → order-detail?orderId=...
  • 任务详情 / 服务市场卡片补 → service / provider；「我的」补 → apply
  • 加守卫：已注册的非 tabBar 路由必须至少有一处入站跳转
P1-27 个骨架页空态文案把「功能未上线」写成「你还没有做」
证据service「服务还没上架」· provider「还没有主页内容」· apply「还没开始认证 / 完成认证就能接单啦」（页面根本没有认证入口）· skill「还没有技能画像」· chat「还没有会话」· verify「还没提交认证材料」· os/result「交付包还在准备」
对照写法正确的：settings「设置项准备中 / 将在这里逐项开放」、order-list「即将上线」。
为什么是问题与红线「不许用假数据/误导冒充功能」冲突，且同批骨架页两种口径并存，用户会得出错误结论。
修复方案
  • 统一改用 utils/not-ready.ts 口径：标题「XX 功能开发中」，副文案「已规划、尚未上线」
  • 把文案抽成 not-ready.ts 导出常量，避免 7 处再次漂移
  • 加守卫禁止骨架页出现「还没有 / 还没开始」句式
P1-3LLM 延迟抖动 + 超时重试，最坏让用户等 185 秒
现象同一提示词实测 65132ms / 9503ms / 7166ms（抖动近 10 倍）；verify:tools 中 generate_outline 实测 69995ms；OS 对话单条 16.3s。
根因已定位：openai-compatible.provider.ts 每次尝试 AbortSignal.timeout(60000)，maxRetry=3，退避 1s/4s → 最坏 60+1+60+4+60 = 185 秒。实测 69995ms 正是「60s 超时 + 1s 退避 + 9s 重试成功」的指纹。
放大因素LLM_FALLBACK_MODELS= 刻意留空 → 主模型过载时无跨模型兜底，只能等满 185s 后硬失败。
归因抖动来自服务商侧排队，不是代码 bug —— 但代码放大了它的后果（超时值 × 重试次数）。
修复方案
  • 按工具分档设超时：短任务（意图/总结/提示词）降到 20~25s，长任务保留 60s
  • 重试预算改为总时长上限（整次 ≤90s），而非「每次 60s × 3 次」
  • 补跨服务商降级：需新增独立 LLM_FALLBACK_BASE_URL / API_KEY
  • os/sessions/:id/messages 是同步阻塞，建议改 SSE 或先返回「思考中」再推送
P1-4ASR 语音转文字间歇性挂起超时，失败率约 35%
现象6 轮样本 2 轮失败（33%），8 轮扫描 3 轮失败（38%）。成功时仅 78~97ms。
失败原文The operation was aborted due to timeout
关键点失败时连 120s 超时都没返回（ASR_TIMEOUT_MS=120000），即服务商 /audio/transcriptions 端点偶发无限挂起 —— 不是 400、不是参数错。
影响speech_to_text 是 9 个 active 工具之一，工具页展示为「可用」→ 用户有 1/3 概率等 2 分钟后收到超时错误。
修复方案
  • 降低超时：ASR 正常 <100ms，把 ASR_TIMEOUT_MS 从 120000 降到 15~20s，快速失败
  • 加失败重试 1 次：这类「挂起」重试通常能成功（ASR Provider 目前无重试）
  • 确认该错误不被 BizException 吞成确定性失败（参考已踩过的 UnusableOutputError 教训）
  • 把 verify:siliconflow 的 ASR 段改为多次采样再判定，避免单次采样把偶发当稳定
P1-5后端 404 的原始框架报文直接弹给用户
现象用户填完整张发布表单点「发布」→ toast 显示 Cannot POST /api/v1/station/tasks
实测响应: {"code":40400,"message":"Cannot POST /api/v1/station/tasks","data":null,"traceId":"-"} request.ts:203 → new Error(body.message) request.ts:280 → showToast(e.message)
命中点publish:251 → stationApi.publish · task:94 → stationApi.apply · order-detail:88/128/158 → orderApi.pay/accept/refund
对照task 的「选定服务者/关闭需求」、workbench 的「报名接单」、order-detail 的「订单交付/要求修改」均已用 showNotReady ✅ → 属「只改了一半」
修复方案
  • 上述 5 个调用点改为 showNotReady(...)，与已改部分保持一致
  • 更稳：在 request.ts 增加错误文案映射层，code===40400 统一转「该功能尚未开放」，从根上杜绝原始报文泄漏
  • 扩展 audit-api-routes.mjs：调用缺失路由的页面必须导入 showNotReady
P1-6真机微信登录从未被验证过
证据.env 的 WECHAT_SECRET 为空 → 走开发模式伪 openid（实测返回 openid:"dev_c43d94d0"，dev_ 前缀即降级路径）。
做得对的降级显式可辨：打 warn 日志 + 响应带 X-Provider: mock，符合红线 10 ✅
问题M0-16 验收要求是「真机登录成功」，目前只证明了开发降级路径 —— 真实 code2session 链路（含 session_key、unionid、错误码处理）一次都没跑过。
修复方案
  • 填入真实 WECHAT_SECRET；按 P0-3 配好真机可达地址后走一次完整登录
  • 补 verify:wechat：用真 code 打 code2session，断言 openid 非 dev_ 前缀
  • 覆盖失效 code / 过期 code 的负向用例
