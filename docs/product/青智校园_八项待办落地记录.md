## 二、一个贯穿全局的决策：侧车**没有**换成 FastAPI

`requirements.txt` 里列着 FastAPI，那是"进实现阶段"的原始计划。实际落地时保留了标准库骨架，理由：

1. 侧车真正的依赖是 **ffmpeg / soffice / pandoc 这类系统二进制**，不是 Web 框架。
   换框架不会让任何一个能力变得可用，只会凭空多一层必装依赖；
2. "零依赖也能起来"有实打实的运维价值 —— 服务器上 `python -m services.media` 就能拉起并自报健康。
   换成 FastAPI 后**没装依赖时连 `/health` 都没有**，排障反而变难（连"服务在不在"都问不出来）。

改法是在 `services/shared/http.py` 上做**向后兼容的扩展**：`routes.py` 的 `ROUTES`
仍是「已定义能力」的唯一清单，另加一个 `IMPLEMENTED` 声明集合，启动时对账。

| 情形 | 状态码 | 响应头 |
|---|---|---|
| 已注册 handler 且成功 | 200 | `X-Provider: real` + `X-Capability` |
| 已在 ROUTES 定义但未实现 | 501（code 50341） | `X-Provider: mock` |

新增 `SERVICE_STAGE`（默认 `skeleton`）进响应头与 `/health`：
**能力做完必须改掉它**，否则监控里"已完成的服务"仍显示为骨架。

## 三、逐条说明

### 1. 转换服务 —— 新建 `services/convert`

- 能力矩阵：soffice 走 `docx/ppt/xlsx/html/txt → pdf`；pandoc 走 `md/html/docx` 互转。
- `GET /convert/capabilities` 是**只读自检端点**：不发文件就能问清"这台机器装了哪些引擎"。
- soffice 调用带 `-env:UserInstallation=<临时 profile>`：不隔离的话并发调用会互相抢 profile
  并**随机失败**（报错文案含糊，像是文档损坏）。
- 引擎缺失 → 501，**绝不返回原文件**；产物体积为 0 或未生成也判失败
  （LibreOffice 退出码 0 但不产出是常见行为）。
- 后端：新增 `DocConvertProvider` 接口（core）+ `HttpConvertProvider`（api）。

⚠️ **本机 LibreOffice / Pandoc 均未安装**，所以只验证了"缺引擎时明确降级"这条路径。

### 2. 媒体侧车 —— 5 个端点全部实现

`services/media/handlers.py`：`probe` / `transcode` / `compress` / `cut` / `subtitle`。
实测产物已用 ffprobe 回验（H.264 High / yuv420p，微信可播）。

**两个值得记住的点**：

- **编码器不能写死**。本机 ffmpeg 是 LGPL 构建，`--disable-libx264 --disable-libx265`，
  "转 mp4 就用 libx264"会直接报 unknown encoder。`ffmpeg.py` 改为运行时读 `-encoders` 挑候选，
  且**硬件编码器失败自动降级**（只对 `*_nvenc/_amf/_qsv` 降级；软件编码器失败=输入有问题，直接失败）。
  实测本机 nvenc 与 amf 都失败、自动落到 qsv —— 这条降级链路是被真实环境验证过的。
- **GIF 只能用 `gif` 编码器**：gif muxer 不接受 H.264/MPEG-4 流
  （实测报 `gif muxer supports only codec gif for type video`）。画质由 palettegen 决定。

`services/ai` 侧只实现 `/ai/matting`，其余 6 条仍是 501，且 `handlers.py` 顶部写清了
每条卡在**决策**（去水印、文档解析）还是**工程量**（人声分离需要 GPU 机器）。

### 3. 搜索 —— 定为 MySQL FULLTEXT，并写清为什么

**选型结论：先用 MySQL FULLTEXT（零新组件）**，Meilisearch / ES 留作后续替换（接口不变）。

- 单开 `search_index` 表（迁移 `20260919120000_add_search_index`）：
  跨实体（任务/服务/知识库）要在同一个相关度排序里比较，分散在多张表上做不到。
- ⭐ **中文必须 `WITH PARSER ngram`**。MySQL 默认分词器按**空格**切词，中文正文会被当成
  一个整词 —— 检索"摄影"匹配不到"校园摄影服务"，而且**不报错、永远返回空**。
  这类"静默错"是本次最值得记的一条。
- 检索走**自然语言模式**而非布尔模式：布尔模式下 `+ - * " ( )` 都是操作符，
  用户输入 `C++` 会被当成语法而不是内容。
- 附带超时保护：FULLTEXT 一旦退化成全表扫描会一直占连接，而小程序请求只有 30 秒。

⚠️ `SEARCH_DRIVER` 默认仍是 `mock`：切 `mysql` **必须先跑迁移**，不做隐式切换。
本机 MySQL 在跑但迁移未执行，因此 `mysql` 路径未实测。

### 4. 短信 —— 厂商未选型，只做与厂商无关的适配器

`HttpSmsProvider`：可配字段名的 HTTP 网关 + 手机号校验 + **日志脱敏**。

没有写阿里云/腾讯云签名实现，理由写在代码里：服务商尚未选型，而带签名的实现
（阿里云 RPC HMAC-SHA1、腾讯云 TC3-HMAC-SHA256）**没有真实凭证就只能靠猜**，
签错的表现是"接口返回签名错误"，排查成本很高。选型定了之后新增一个实现同一接口的
Provider 即可，业务代码零改动。

脱敏这条不是洁癖：`[mock-sms] 验证码短信 138xxx: {"code":"1234"}` 这种日志
等于把"手机号 + 验证码"这一对完整凭证写进了日志文件。

### 5. 内容审核 —— 微信官方接口 + 自建词库

判定顺序：**本地校园词库**（不联网、不花配额）→ **官方 `msgSecCheck`**（唯一主判据）。
词库排在前面只是省配额，覆盖面一点没少。

两处与其它 Provider **相反**的策略（这是本条最需要记住的部分）：

1. **fail-closed**。拿不到 token / 接口报错 → 抛 `50364` **拦内容，不放行**。
   队列、缓存、限流挂了可以 fail-open（它们是优化）；审核挂了必须 fail-closed，
   因为放行一条违规内容的代价是合规事故，而拦住的代价只是用户重试一次。
2. **图片审核是异步接口**。`mediaCheckAsync` 只收**公网 URL**、只返回一个 `trace_id`，
   结论要等微信推送到开发者服务器 —— 也就是说它**在任何时刻都不会给出"可以放行"的即时答案**。
   所以 `checkImage` 返回 `pass:false + action:'review'`（结果到达前不放行），绝不返回 `pass`。

另外：token 用 `/cgi-bin/stable_token` 而不是老接口 —— 后者在多个实例并发调用时会互相顶掉，
症状是"审核偶发失败"，极难定位。

#### 补记（同日第二轮）：**Provider 写好了 ≠ 内容被审过**

上面这一节描述的只是 **Provider**。它当时**没有任何调用方** ——
所有 UGC 写入口（改昵称、填交付说明、写退款理由、发 AI 会话消息）实际处于裸奔状态。
这类问题**单测查不出来**：单测直接 `new` 一个 service，永远不会暴露"没人 new 它"。

现在统一走 `apps/api/src/modules/moderation/`（`@Global`）的 `ModerationService`，
由它负责三件必须在一处做对的事：

1. **fail-closed** —— 把 Provider 抛出的**任何**异常（含未预期的 `TypeError`）统一翻译成 `50364`，
   绝不吞掉、绝不放行；
2. **补齐 openid** —— 微信 v2 必填，而业务 service 手上只有 `userId`。
   让每个调用点自己查一次用户表，一定会有人忘了查；
3. **区分 reject 与 review 的文案** —— 前者"改内容就能过"，后者"改多少遍都一样，只能等"。
   报同一句"请修改后重试"，第二种情况的用户会反复改到放弃。

已接线的入口：`PUT /user/me`（昵称/简介）、`POST /orders/:id/deliver`（交付说明）、
`POST /orders/:id/refund`（退款理由）、`POST /os/sessions/:id/messages`（会话消息）。
发布需求 / 报名 / 评价的入口**本身还没开工**，开工时注入 `ModerationService` 即可。

同时修掉一处**假结论**：`MockModerationProvider.checkImage` 原返回 `pass:true` ——
等于宣称"这张图我审过了、没问题"，而 Mock 根本没有审图能力（红线 10）。
现改为 `pass:false + action:'review'`。它的 `checkText` 也改为复用
`CAMPUS_LEXICON`（原先自带一份 5 词短表），避免出现"本地放行、线上拦截"这种最难查的偏差。

复验：`npm run verify:moderation`（25 项断言，含"被拦后**没落库**"与"正常内容**不误伤**"）。

⚠️ **仍未闭环**：① 驱动仍是 `mock`（`WECHAT_SECRET` 已配，切 `MODERATION_DRIVER=wechat` 即可启用官方接口，
但本地保持 mock 是为了让验证脚本可确定性复现）；② **图片审核未接线**（异步接口要公网 URL）。
详见 `docs/dev/CONFIG-GAPS.md` 三之二。

### 6. 知识库前端入口 —— `pkg-toolbox/knowledge`

后端 5 个接口早就绪并验证通过，但小程序端**一个入口都没有**（能力可用而用户看不见 ≈ 没做）。
本次补上页面 + 路由 + 工具箱页的入口。

**两种模式并列**，因为语义完全不同：

- **问一句**（`/knowledge/ask`）：检索后由模型组织成一段话，带引用；
- **查原文**（`/knowledge/search`）：只返回命中的原文切片，不经过模型。

做作业查校规时，用户要的往往是后者 —— 看到的就是原文。

⭐ **`grounded === false` 必须用完全不同的样式渲染**（警示色 + "未在知识库中找到依据"）。
这是整套 RAG 设计里最关键的取舍（检索不到时不许模型硬答），但它极易在界面上被抹平 ——
一旦两种情况渲染成同一个答案卡片，用户就再也分不清"知识库里有"和"模型编的"。

> ⚠️ **2026-10-08：本条的"前端入口"已移除** —— 独立页 `pkg-toolbox/knowledge`、
> 工具箱的 `kb-row` 卡片、`app.json` 的 `knowledge/index` 路由与 `knowledgeApi` 一并下线，
> 本小节保留是为了说明**为什么界面上找不到它**，不是漏做，**不要再补回独立入口**。
> 后端 `knowledge` 模块与 5 个 `/knowledge/*` 接口**原样保留**，知识库能力改由 AI 助手的
> `search_knowledge`（见下一条）暴露给用户。

### 7. `search_knowledge` 的 tool calling —— 补在 OsService

清单说得准确："真正缺的不是知识库（服务已就绪），而是 **OsService 完全没有 tool calling**"。
在此之前 `sendMessage` 就是**一次** `llm.chat()`。

新增 `os-tools.ts`（工具规格 + 执行器）与 `chatWithTools` 循环。三处必须守住的边界：

- **最多 2 轮**。每轮都是一次完整模型往返（数秒），而小程序请求超时只有 30 秒，
  轮数给多了"等超时"会变成常态；
- **轮次用尽必须兜底再要一次不带工具的答复**，否则最后一轮的结果是"模型发起了调用"，
  用户会收到**空消息**；
- **工具结果只活在当轮上下文**，不进 `os_message` —— 几千字原文会把会话列表撑爆。

配套改了 `@qz/core` 的 `LlmMessage`（加 `toolCalls`）与 Provider 的 `buildBody`
（回填 `tool_calls`）。**少了这一步，模型会重复发起同一个调用** —— 协议要求，不是可选。

> ⚠️ **遗留了 4 个月才补上的一步（2026-09-19）**：tool calling 补完之后，
> `seed.ts` 里 `search_knowledge` 的 `status` **一直没跟着改成 `active`**。
> 原因不是漏改，而是改不动 —— `check-tool-status.mjs` 的判据只有"执行器是否注册"，
> 而 `search_knowledge` 是**内部能力**（`source: 'internal'`，由 `os-tools.ts` 进程内直调，
> 不进执行器），一改就误报"标为 active 但实际跑不通"。
> 于是**状态字段成了守卫的奴隶**：功能是好的，`seed` 却在说它没上线。
> 现在守卫已补上内部能力识别，状态恢复如实（`check:tools` 输出 `30 个 active`）。

### 8. `remove_background` —— 真跑通，并转正

- `SidecarImageProvider` 按能力分流：压缩/转格式/增强留本地 Sharp（纯 CPU、毫秒级，
  没必要走网络），**只有抠图发远程**。不为一个能力把整族改成远程，也不让 Sharp 假装能抠图。
- `services/ai/matting.py` 的白名单是**代码级强制**（`WHITELIST={u2net}`），
  超白名单 **fail-fast 而不是静默回退** —— 静默回退会让运维以为"我换的模型生效了"。
- 实测：JPEG → RGBA PNG，四角 `alpha=0`、中心 `alpha=255`、79% 像素全透明。
- `seed.ts`：`remove_background` 由 `planned` → **`active`**；
  `check-tool-status.mjs` 的 `PROVIDER_NOT_READY` 豁免**清空**；
  `verify-tools.mjs` 补上它的验证用例。
- **`npm run verify:tools` → 10 个 active 工具全部端到端跑通**（抠图 168ms）。

**状态改动必须三处同步**（seed / 状态守卫 / 验证脚本）。只改 seed 会让守卫继续按
旧假设豁免它 —— "能力做完了但验证脚本还当它不存在"是最危险的一种状态。

## 四、本轮踩到的三个"不报错但会骗人"的坑

1. **`import type` 不能用在 Nest 的构造参数上**。`emitDecoratorMetadata` 需要**运行时**类引用，
   而 `import type` 会被完全擦除 → 启动时报
   `Nest can't resolve dependencies of the OsService (... ?)`，且那个参数显示成 `Function`。
   **编译过、单测过（单测是手工 `new` 的）、只有真启动才炸。**
2. **`nest start --watch` 在本环境起不来**：它会批量删除 `apps/api/dist`（几百个文件），
   被沙箱的 safe-delete 拦下。验证时改用 `PORT=3100 node apps/api/dist/main.js`。
3. **源码里写 `\0` 会把真的 NUL 字节写进文件**，文件随即被判为二进制、diff 与逐行审查失效。
   二进制魔数比较一律用数值（`b[0] === 0x49`）。
   （附带：curl 是原生二进制，不认 MSYS 的 `/c/...` 路径，必须给 `C:/...`。）

# 第二部分：没跑通的清单（同日第二轮）

> 用户又贴了一张「二、没跑通的」截图。核完发现 4 条**性质完全不同**：
> 有的只是"进程没起"，有的是"只差接线"，有的是"整个里程碑没做"。
> 分开处理比一律"去修"重要得多 —— 混在一起会让"最该先做的"被淹没。

## 第 1 条 抠图跑不起来 —— ✅ 已修（流程问题，不是代码问题）

真实原因：`services/ai` 侧车进程没启动。上一轮验证完顺手停了侧车，清单是在那之后生成的。

**修法**：新增 `npm run dev:sidecars`（`scripts/dev/run-sidecars.mjs`），
一条命令起三个侧车，任一退出就一起收摊。配套 `npm run dev:convert`。

这条命令存在的理由本身就是个教训：**三个服务要开三个终端**这个摩擦点，
会让"某个功能单独不可用"既不显眼、也不在 /health 里变红。
顺带修掉 `SERVICE_STAGE` 未配会退回 `skeleton` 的问题（已完成的服务会显示成骨架）。

### 第三轮：驿站写路径（发布 → 报名 → 选定 → 生成订单）

补的是这条链上**唯一空着的一段**。之前的状态是：
发布页点「发布」→ `Cannot POST /api/v1/station/tasks`；
任务页点「报名」→ 同样 404；发布者点「选定」→ **弹"已选定"但没调任何接口**（假成功）；
工作台「推荐给你的任务」的匹配度是 `Math.max(60, 95 - i * 7)` —— **按列表序号递减的假数字**。

| 任务 | 接口 | 关键决策 |
|---|---|---|
| M3-01 | `GET /station/categories` | 分类从接口读（唯一真源）。发布页原先有**第三份**分类拷贝，而守卫只覆盖大厅页那份 |
| M3-06 | `POST /station/tasks` | 直接落 `published`：内容安全是**同步 fail-closed** 的，再排一次人工预审只会让"发布"变异步，换不来合规收益 |
| M3-07 | `POST /station/parse` | 走 `intent` 档（结构化抽取，不是创作）。**估价只用真实成交均价**，样本 < 3 单则隐藏 —— 不编造价格区间 |
| M3-09 | `GET /station/match` + 列表附带匹配度 | 权重照抄设计文档（技能 40 / 信用 20 / 完成率 15 / 距离 15 / 价格 10 / 活跃度 5）。⚠️ **合计 105 不是 100**，故按满分归一化，否则会出现「匹配度 105%」 |
| M3-10 | `POST .../apply`、`POST .../select` | 报名靠 `@@unique(taskId,providerId)` 收口并发；选定与建订单**同一事务** |
| M3-08 | `POST .../close` | 只在未选定时可关闭（已选定就该走取消订单，M3-15） |
| — | `GET .../applications` | **发布者此前永远看到"还没有人报名"** —— `applications` 从未被任何接口填充过 |

**顺手修掉的四个"不报错但会骗人"的问题**（都不在报告里，是本轮看代码发现的）：

1. **假匹配度**（`workbench/index.ts`）—— 按序号递减的百分比，静态守卫拦不住
   （守卫只查"声明了 `DEMO_*` 常量却没挂标记"）。现在服务端真算，且**没算出来就不渲染这一行**。
2. **工作台"我的任务"是别人的单** —— 用 `status=assigned` 查，拿到的是**全站所有已选定任务**。
   这不是显示问题，是越权看到他人订单。现在走服务端 `role=provider` 过滤。
3. **`source` 字段被 Zod 静默丢弃** —— 客户端从 v1 就在传，schema 里一直没有，
   于是所有任务都落成 `manual`。加了 `source` 枚举。
4. **AI 解析的预算差 100 倍** —— 后端给「分」、表单填「元」，而 `applyParsed` 直接
   `String(parsed.budget)`。300 元会被预填成 30000 元，而"预算 ¥30000"在表单上看着只是个偏高的正常数字。

**验证**：`npm run verify:station` —— **53 项断言**。除了常规的正向链路，专门钉住两类：
- **没落库**：违规标题/描述/报名留言被拦后，库里不能已经有记录（"先写后查"是最常见的实现错误）；
- **分数是真算的**：同技能服务者的匹配度必须**严格高于**无技能者
  （假实现按序号递减，与技能无关 —— 任何"分数在 0~100 之间"的弱断言都拦不住它）。

一条说明：这 16 个接口在 `audit:api` 里原本**已全部登记在 `KNOWN_MISSING`**，
所以它们是"已知缺口"而不是"漏了"。现在驿站与订单两段的豁免**已删除**
（豁免清单会反向提示"豁免已失效"，照删即可）；OS 编排 3 条与消息 1 条仍在表里。

### 第三轮之二：服务者入驻认证（M3-02）

补的是"人怎么变成服务者"这一步 —— 没有它，**报名接单那条规则谁也走不到**：
`assertIsProvider` 要求 provider 角色，而当时没有任何途径获得它
（除了 seed 里那个已认证的演示账号）。

之前的状态：入驻页 `pkg-station/apply` 只渲染一句"服务者入驻功能开发中"，
且它在静态守卫里是**孤岛页**（全仓库零入站跳转）—— 既没有入口，也没有页面；
认证中心 `pkg-mine/verify` 的主按钮弹"认证入口即将开放"，而那个入口并不存在。

| 接口 | 说明 |
|---|---|
| `GET /provider/schools` | 学校列表（公开），入驻表单的学校选择器 |
| `POST /provider/apply` | 提交入驻申请（学生身份 + 技能标签 + 材料） |
| `GET /provider/profile` | 我的服务者资料与认证状态（含**驳回原因**） |
| `GET /provider/verifications` | 申请列表（**仅管理员**，M0-23 的接口侧） |
| `POST /provider/verifications/:id/review` | 审核：通过 / 驳回（**仅管理员**） |

**几个关键决策**：

1. **身份信息存快照，不读 `user` 表**。审核要看到的是"**这次提交的**是谁"。
   用户事后改了资料，历史申请记录不能跟着变 —— 否则"当初凭什么通过的"再也说不清。
   为此给 `verification` 加了 4 列（`real_name` / `student_no` / `school_id` / `college`）。
2. **材料必须属于申请人自己**。不做这个校验，拿到别人的文件 id 就能把别人的学生证
   当自己的材料交 —— 而文件 id 是 uuid、又能从列表接口拿到，这不是理论风险。
3. **"驳回必须给原因"由 schema 的 `refine` 强制**，不是只在界面提示。
   只把 `reason` 声明成 optional，服务端仍能存下一条没有原因的驳回。
4. **通过时三处必须同一事务写全**（`verification` + `user_role` + `user_profile`）。
   分开写会出现"有角色没技能"（匹配算法把他算成零技能、永远排最后）
   或"有技能没角色"（界面显示已认证、报名却报 40312）—— 两种都**不报错**。
5. **允许被驳回后重新提交**（新建一条、保留历史），但**审核中不允许重复提交** ——
   否则管理员会看到同一人的多条待审记录，无法判断哪条是当前意图。

**前端**：入驻页做成真实的三步表单（学生身份 / 技能认证 / 服务承诺），
并区分**五种状态**（加载 / 出错 / 已认证 / 审核中 / 可填写）——
已通过和审核中**都不显示表单**（重复提交会被 40901 拒，而用户看到的是一个填得好好的表单点不动）；
被驳回时**把原因显示在表单上方**。
认证中心改为真实状态页，并按状态给下一步动作；它指向入驻页，`apply` 因此不再是孤岛页。

**验证**：`npm run verify:provider` —— **33 项断言**，专门去撞 M3-02 的两条验收标准：
- **未认证无法接单**：认证前报名 → 40312；认证后报名 → 201（两边都断言，只测一边会漏掉"认证了却接不了单"）；
- **驳回必须给原因**：不写原因 / 原因过短 → 400；写了 → 原因原样保存且申请人能读到。

⚠️ **仍未闭环**：**管理后台（M0-23）未开工**，所以审核目前只能通过接口/脚本进行。
入驻申请提交后会停在"审核中"，没有人工审核的入口 —— 这是 M0-23 的缺口，不是 M3-02 的。

**搜索这一条的验证方式值得记**：脚本断言的是**命中数**而不是"查询没报错" ——
因为中文 FULLTEXT 的典型失败模式是**静默返回空**（默认分词器按空格切词），
只有真跑一次中文检索才发现得。已验证：检索「摄影」命中「校园摄影服务」、
词只在正文里也能命中、无关词返回 0 条。

**`notify` 为什么刻意不做**：微信订阅消息的数据字段名（`thing1` / `time2` …）
**由你在后台建模板时决定**，代码猜不得。猜错的表现是"推送静默失败"，
而这种坏法比报错难查得多。要落地需要你提供：模板 id + 每个字段的键名映射。
届时新增一个实现同一个 `NotifyProvider` 接口的 Provider 即可。

## 本轮新踩的坑

1. **单测里的"多余实参"是定时炸弹**。`tool-executor.spec.ts` 给构造器传了 6 个实参，
