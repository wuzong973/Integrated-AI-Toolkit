## 1. 结论摘要

**整体判断：核心链路（登录 / 文件 / AI 工具箱 / 实时进度）已经真实跑通，可以演示；但"驿站 + 订单"两大业务域尚未开工，且存在 3 个会阻断"真机验收"的 P0 问题。**

实测跑通的闭环（不是"代码看起来对"，是真跑出结果）：

| 链路 | 实测结果 |
|---|---|
| 登录 → JWT → 鉴权接口 | ✅ HTTP 201 / 225ms，6 个鉴权接口全 200 |
| 文件 presign → 直传 → confirm → 列表 → 下载 → 删除 | ✅ 8/8，含"伪造签名被拒 403" |
| 上传文件 → 调 `summarize_text` → 作业 → 产物 | ✅ 6 秒成功，产物是**真实高质量 Markdown**（已下载核对正文） |
| WebSocket 实时进度 + 断线重连补齐 | ✅ 进度序列 0→0→15→55→90→100 单调不减 |
| AI 意图识别 | ✅ 5/5 命中 |
| 9 个 active 工具端到端 | ✅ 9/9 真能跑 |

**规模事实**（2026-09-20 复核并回写；本节数字全部取自守卫的实时口径，**引用时请重跑对应命令**）：
后端注册路由 **86** 个（`npm run audit:api`）；小程序调用 **65** 个，**已无"后端未开工"缺口**（曾登记的 16 条随 M3 各模块落地全部清零）；
工具 **41** 条 = 用户可见 33 + Agent 内部 8，状态 **active 32 / planned 9**（`npm run check:tools`）；
服务分类 **9** 个（`npm run check:categories`）；页面路由 **32** 个（主包 7 + 分包 25，`apps/mp/app.json`）；单测 **888** 个全过（`npm test`）。

### 🔴 P0-2：Redis 未运行，作业队列已降级为进程内执行

| 项 | 内容 |
|---|---|
| **现象** | 后端启动日志 `[-] WARN Redis Redis 不可用，降级运行`；`/health` 返回 `redis:"down"`、`queue.degraded:true`、`pending.tool.job:-1` |
| **证据** | `curl /health` 实测如上；`Get-NetTCPConnection -LocalPort 6379` **无监听**；Redis 仅由 `docker-compose.yml` 提供，而本机 `docker: command not found` |
| **降级的真实代价** | 实测降级路径**能跑通**（作业 6 秒成功），但代价是：① 无跨进程并发控制（`QUEUE_WORKER_CONCURRENCY=2` 只在单进程内生效，多实例部署即失效）；② 作业状态不持久化，**进程重启即丢**；③ 无 `deadLettered` 统计（返回 -1 = 不可知）；④ 无 PEL，无法做失败重投 |
| **做得好的地方** | 降级**不静默**：打 warn + `/health` 暴露 `degraded:true`，符合"M0-11 判据：降级后是否会静默丢数据"。这一条**不需要返工**，只需补部署 |
| **修复方案（已实施 ②③）** | ① **待你操作**：装 Docker Desktop 或本机装 Redis 7（`redis-server --appendonly yes`），使 `docker compose up -d redis` 可用；② ✅ 已在 `docs/dev/ENV.md` 增加"Redis 为**生产必需**组件，缺失时禁止上线"的硬性说明（附降级后失去的四项能力）；③ ✅ `/health` 的 `status` 改为**三态**：`ok` / `degraded` / `down`，并新增 `degradedReasons` 说明原因。**HTTP 状态码刻意保持 200**（它是状态报告不是准入闸门，返回 503 会让冒烟脚本在降级环境下误判失败）；④ ✅ 附带修掉了 **N-1**：`queue.degraded` 在 Redis 挂掉但尚未投递过作业时误报 `false` |
| **落点** | 环境部署；`apps/api/src/modules/health/`；`docs/dev/ENV.md` |
| **任务编号** | M0-09 / M0-11 |

|---|---|
| **现象** | 同一提示词实测 **65132ms / 9503ms / 7166ms**（3 次），抖动近 10 倍；`verify:tools` 中 `generate_outline` 实测 **69995ms** |
| **根因（已定位）** | `apps/api/src/infra/providers/llm/openai-compatible.provider.ts`：`postWithRetry` 每次尝试 `AbortSignal.timeout(60000)`，`maxRetry=3`，退避 `1s / 4s` → 单个模型最坏 `60+1+60+4+60 = 185 秒`。实测 69995ms 正是「**60s 超时 + 1s 退避 + 9s 重试成功**」的指纹 |
| **放大因素（初版报告低估了）** | ① `LLM_FALLBACK_MODELS` 配了降级模型时，**总时长要再乘模型数**：`2 × 185s = 370 秒`。② 而小程序 `request.ts` 的超时只有 **30 秒** —— 前端早已断开，后端还在继续打请求，**每次都照样消耗供应商额度**。钱花了、用户什么都没得到、日志里还看不出异常 |
| **其他实测延迟** | OS 对话单条 **16.3s**（仅 1 次 LLM 调用）；三档采样：intent 平均 3716ms / generate 3616ms / plan 3094ms |
| **归因判断** | 抖动来自**服务商侧排队**，不是代码 bug —— 但**代码放大了它的后果**（超时值 × 重试次数） |
| **修复方案（已实施 ①②）** | ① ~~按工具分档设超时~~ → 改用更彻底的 **`LLM_TOTAL_BUDGET_MS` 总时间预算**（默认 45s）：无论模型数 / 重试数怎么配，一次逻辑调用的墙钟时间**不会超过它**。预算耗尽时**主动停下**而不是"再试最后一次"——剩余不足一次典型请求时再发只会超时，却照样花钱；退避等待也会被压缩，避免 `16s` 退避一口吃掉 `20s` 预算；② 单次尝试超时改为 `min(LLM_TIMEOUT_MS, 剩余预算)`，防止最后一次冲爆总预算；③ **待办**：补跨服务商降级（需独立的 `LLM_FALLBACK_BASE_URL` / `LLM_FALLBACK_API_KEY`，同服务商换模型名兜不住）；④ **待办**：`os/sessions/:id/messages` 仍是**同步阻塞**（单条 16.3s），建议改 SSE 或先返回"思考中"再推送；⑤ 前端 `pkg-toolbox/run` 已有进度层与 WebSocket，确认长时间转圈时给"仍在处理，可离开页面"提示 |
| **落点** | `apps/api/src/infra/providers/llm/openai-compatible.provider.ts`、`apps/api/src/modules/os/os.service.ts`、`.env` |
| **任务编号** | M1-07 / M2-03 |

### 🟠 P1-4：ASR（语音转文字）间歇性挂起超时，失败率 ~35%
